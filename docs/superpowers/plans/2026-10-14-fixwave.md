2. A colour fix applied in the wrong layer (CLI only, or GUI only) — the RGB888 frame from `Machine::screen` itself must be correct. Owned by Task 2.

4. A speed-up that changes guest-visible behaviour — difftest and all milestone tests must stay green. Owned by Task 4.

### Task 1: Keypad matrix — arithmetic keys and full verification

**Files:** `crates/evo-hw/src/dev/keypad.rs` (`KEY_NAMES`), `crates/evo-core/src/keys.rs` if names live there, `docs/hardware/keypad.md`, tests in `crates/evo-hw/tests/keypad.rs` and `crates/evo-core/tests/milestones.rs`.

Finding (confirmed by two verifiers, reproduced on bundle 7.1.0.4421 with `--keys` from a home-screen save state): `KEY_NAMES` puts add/sub/mul/div/power at matrix (6,1)..(6,5) copied from the CE. On the Evo OS, `2 add 3 enter` shows `23`; `sub` types `+`; `mul` types `−`; `div` types `×`; `power` types `÷`. So the Evo's column order in that group is shifted: + at the former `sub` position, − at `mul`, × at `div`, ÷ at `power`, and `^` sits where the OS reads it (find it — the BSP USB-HID table at NS 0x0018_421C puts keypad + − × ÷ on codes 0x0b–0x0e; locate `^` from the OS key handling or the key-test grid at NS 0x0015_6244).

- [ ] **Step 1:** Write an env-gated release test `all_keys_type_expected_text` that boots to the OS calculator screen (provisioned or via the M4 Self-Test exit), then for every key with a typed glyph presses it and reads back the OS's edit buffer or screen text (reuse the M4/M3 harness; if text readback is impractical, compare the rendered screen region against the expected glyph by checking the OS's input-buffer RAM — find it with GDB) and asserts the expected character; keys without glyphs (2nd, alpha, mode, del, arrows, clear, math, apps, prgm, vars, stat, y=, window, zoom, trace, graph, on) are asserted by the screen/menu they open. Capture RED.
- [ ] **Step 2:** Fix `KEY_NAMES` so every key matches; update `docs/hardware/keypad.md` (key table + resolve open question 2) and any CE-layout claim that is now wrong.
- [ ] **Step 3:** Tests GREEN; gates; commit `fix(evo-hw): Evo keypad arithmetic column order`.

### Task 2: LCD colour order (red/blue swapped)

**Files:** `crates/evo-hw/src/dev/lcdc.rs` (frame decode), possibly `crates/evo-hw/src/dev/spi.rs` (ST7789 MADCTL BGR bit), `crates/evo-core/tests/milestones.rs` (`M3_SCREEN_SHA256`), `docs/hardware/lcdc.md`.

Finding (controller visual check): the OS home screen renders the selected tile and graph strokes orange/brown and the MODE-screen highlight orange; on hardware they are blue (TI-84 Evo web emulator screenshot: blue selection, green secondary). Green is unaffected → R and B are swapped somewhere in RGB565/BGR handling.

- [ ] **Step 1:** Determine from evidence which layer owns the order: PL111 `LCDControl` BGR bit (bit 8) as programmed by the BSP, the panel's MADCTL bit 3 (BGR) sent over SPI, and the framebuffer pixel format. Document the chain in `docs/hardware/lcdc.md`.
- [ ] **Step 2:** Test first: a unit test that a framebuffer pixel the OS writes for a known colour (derive from the BSP/OS palette constant of the selection blue, cite its address) decodes to blue-dominant RGB888; plus update the M3 test so its approved hash is re-derived only after a screenshot (kept outside the repo) shows blue selection and the report describes it.
- [ ] **Step 3:** Fix; regenerate `M3_SCREEN_SHA256` from the corrected frame; GREEN; commit `fix(evo-hw): LCD red/blue channel order`.

### Task 3: Factory provisioning — boot straight to the OS

**Files:** `crates/evo-core/src/provision.rs` (new), `crates/evo-core/src/lib.rs`, `apps/evo-cli/src/main.rs` (new subcommand `provision`), tests `crates/evo-core/tests/milestones.rs`, `docs/hardware/boot-flow.md`.

Context (ruling R24): a fresh flash boots the BSP into its Self-Test app because ITS UID `0x1f61e867_8ce70001` ("boot to OS") is missing. The firmware's own Engineering menu (hold `alpha`+`sin`+`enter` across reset; menu object at NS RAM 0x2001_0EF4, "Boot Select: Self-Test / Calc OS" line at +0x38 written by NS 0x0016_8808) toggles that persistent flag. Provisioning = drive that menu with the keypad, then persist the flash.

- **Produces:** `pub fn provision(m: &mut Machine) -> Result<ProvisionReport, ProvisionError>` — performs: power-on with the Engineering combo held, waits for the menu, navigates to Boot Select, selects Calc OS, exits, and verifies by power-cycling (new `Machine` from `m.nv_state()`) that the next boot reaches image 1 entry `0x0044_BC90` with NO key input. `evo-cli provision <bundle> --flash-file F` runs it and writes F.
- [ ] **Step 1:** Investigate the menu navigation with GDB/trace (which keys select items; how Boot Select toggles; whether a confirmation or reboot is required) and record it in `docs/hardware/boot-flow.md`.
- [ ] **Step 2:** Env-gated release test `provisioned_flash_boots_to_os_without_keys` (RED: fresh flash shows Self-Test), then implement, GREEN. Also assert a second power-cycle from the re-saved flash still boots to the OS (Review Focus 3).
- [ ] **Step 3:** If the Engineering route is impossible, use the documented fallback in this order: (a) Self-Test → Run All Tests passing (find what each test needs), (b) stop and report with evidence — never write ITS directly. Commit `feat: provision a fresh unit to boot the OS`.

### Task 4: Performance — real time or better

**Files:** `crates/armv8m/src/{cpu.rs,decode/*,exec/*}`, `crates/evo-hw/src/memmap.rs`, `crates/evo-core/src/machine.rs`, `benches/` or a `#[ignore]` bench test, `docs/perf.md` (new).

Measured: CLI release run of the real bundle, 1.4e9 cycles in 62 s ≈ 22.6 M cycles/s ≈ 14 % of the 156 MHz guest (Windows, this machine); the GUI reports 67–97 % on the idle home screen (WFI skipping). Busy guest code must reach ≥ 156 M cycles/s.

- [ ] **Step 1:** Add a reproducible benchmark: `evo-cli bench <bundle> --cycles N` (or an `#[ignore]` test) reporting emulated cycles/s for (a) the boot from power-on to the Self-Test screen and (b) a synthetic busy loop on the core; record the baseline in `docs/perf.md`.
- [ ] **Step 2:** Profile (e.g. `cargo flamegraph`/ETW or Windows Performance Recorder; install tools as needed) and record the top hot spots.
- [ ] **Step 3:** Optimize in measured steps, each its own commit with before/after numbers in `docs/perf.md`. Expected levers: a predecoded instruction cache keyed by PC (invalidated on flash/RAM writes to cached pages — flash program/erase, guest stores into executed RAM), a fast path in `MemoryMap` for RAM/flash (direct slice access, no region search per access), avoiding per-step allocation/logging/trace work when disabled, cheaper `sync_bus` (only when a device changed), batching scheduler checks. No guest-visible change: difftest (`--features difftest`, `DIFFTEST_CASES=2000`), tools/testprogs programs, and M1–M4 must stay green.
- [ ] **Step 4:** Stop when busy-code throughput ≥ 156 M cycles/s in release on this machine, or after the levers above are exhausted — report the final number either way.
