# TI-84 Evo Emulator — Plan 3: `evo-gui` Desktop Frontend

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Windows-first eframe/egui desktop frontend: a single vertical calculator (classic TI-84 Plus CE web-emulator layout, Evo web-emulator styling) with a clickable data-driven keypad, PC-keyboard mapping, save-state slots, flash persistence, screenshots and debug panels. It runs against a small backend trait, so it works today on a fake backend and on Plan 1's `Machine`, and gets the LCD, keypad, UART, flash file and save states once Plan 2 lands.

**Architecture:** New binary crate `apps/evo-gui`. The GUI talks to the emulator only through the `EmuBackend` trait (`src/backend/mod.rs`). There are two implementations: `FakeBackend` (deterministic, for tests and golden screenshots) and `MachineBackend` (`src/backend/machine.rs`, the only file that may name `evo_core`/`evo_hw`/`evo_image`/`armv8m`). Emulation runs on the UI thread in time-boxed, adaptively sized chunks each frame. Keypad geometry, legends, colors, the key matrix and the PC-key map are data tables; input logic (tap latching, keyboard translation, pacing, speed metering) is pure and unit-tested; UI behaviour is tested with `egui_kittest`, and golden PNGs and theme-color pixel probes go through kittest's wgpu renderer.

**Tech Stack:** Rust 2024 (toolchain 1.98), `eframe`/`egui`/`egui_kittest` 0.36.2 (MSRV 1.95), `image` 0.25.10 (PNG only), `serde` + `serde_json`, `thiserror`, `clap`, `log` + `env_logger`.

**Spec:** `docs/superpowers/specs/2026-10-13-ti84evo-emulator-design.md` (§6.1 API, §6.4 GUI, §6.5 save states). Also read `docs/hardware/discovery-log.md` (LCD is 320x240, framebuffer at 0x2004_8000, `SystemCoreClock` 156 MHz) and Plan 2 (`docs/superpowers/plans/2026-10-14-peripherals.md`) Tasks 4, 8, 11, 13, 18, 19 and 22, whose Interfaces Task 11 consumes.

**Branch:** `feat/gui`, created from `feat/peripherals` when execution starts.
- Tasks 1–10 target the `Machine` API at Plan 1's tip (commit `548248a`) and use only API that Plan 2 keeps: `Machine::from_bundle`, `run`, `step`, `breakpoints`, `bus.peek`, `bus.log`, `cpu.regs`, `sched.now`. Their tests must also pass on any later `feat/peripherals` tip.

## Global Constraints

- Plan 1's constraints carry over: no TI code, data, images, artwork or dumps committed; `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` pass at every commit; tests needing the OS read env `EVO_OS_IMAGE` and print a skip and return when it is unset; the local bundle path never appears in committed files.
- No TI logo, wordmark, key artwork or TI fonts. Everything is drawn from the layout table with egui's bundled fonts plus DejaVu Sans / DejaVu Sans Mono 2.37 (Task 2). Legends are plain text. The header title is exactly `TI-84 Evo Emulator`.
- Golden PNGs (`apps/evo-gui/tests/snapshots/*.png`) are renders of this UI on `FakeBackend` only, never a frame from the real OS.
- egui-family crates are pinned together: `eframe = "0.36.2"`, `egui = "0.36.2"`, `egui_kittest = "0.36.2"`. Bump them only together.
- Only `apps/evo-gui/src/backend/machine.rs` may refer to `evo_core`, `evo_hw`, `evo_image` or `armv8m` (enforced by a test in Task 10). The GUI never reaches into Plan 2 internals.
- The GUI never panics on user input or files: I/O, bundle, flash-file and save-state errors become toasts (or, before the window opens, a message on stderr and exit code 1). No `unwrap`/`expect` on user-supplied data.
- Emulation runs on the UI thread. One frame runs at most `MAX_FRAME_DT` (0.1 s) of emulated time and at most `WALL_BUDGET` (12 ms) of wall time. No worker threads in this plan. To keep a later move cheap, `EmuBackend: Send` and `FakeProbe` uses `Arc<Mutex<..>>`, so a worker thread would change only `app.rs`. **Decision rule:** Task 10 Step 4 records the GUI's measured speed and the bare interpreter's speed for the real OS (release build). If the GUI is below 100 % while the interpreter alone is above 100 %, a worker-thread follow-up plan is justified; otherwise the UI-thread design stays. *Amended 2026-10-15:* one exception, first-run provisioning (Amendment A2).
- `CLOCK_HZ = 156_000_000` is the one emulated-clock constant (spec §1, discovery log). Task 11 ties it to `evo_core::CPU_HZ` with a compile-time assert.
- Interactive use of `MachineBackend` assumes a release build (`cargo run -p evo-gui --release`). Debug builds stay responsive through the adaptive chunk size (Task 3) but run slowly.
- The default PC-key bindings assume a US keyboard layout.
- Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

- **A2. First-run provisioning runs on a worker thread** (commit `b8be900`). A unit opened with
  no flash file must be factory-provisioned before its OS boots, and `evo_core::provision`
  takes several seconds of wall time even in a release build. On the UI thread that would
  freeze the window with no feedback. So `EvoApp::start_provision` moves the backend to an
  `evo-provision` thread and puts a stand-in (`Away`: no display, no state, every run `Idle`)
  in its place; `poll_provision` takes the backend back when the thread ends, then persists
  the flash on success or shows the error as a toast. While it runs the header and a progress
  toast say "Preparing calculator…", keys do not reach the machine, and Reset, Re-provision
  and the state slots answer "Wait until the calculator is ready". This is the only worker
  thread: emulation still runs on the UI thread as the constraint above says. Re-provision
  (toolbar) runs the same path on demand.
- **A3. `EmuBackend` gained two methods** (Task 1 trait):
  ```rust
  /// True when the machine started from an erased flash and was never provisioned.
  fn needs_provision(&self) -> bool;
  /// Factory provisioning; slow, so the app calls it on a worker thread. Does not write the
  /// flash file. Breakpoints are kept. On Err the machine is left where provisioning stopped.
  fn provision(&mut self) -> Result<(), BackendError>;
  ```
  with `BackendError::Provision(String)`. `persist` is a no-op while `needs_provision()`, so a
  failed first run is provisioned again at the next launch, and `MachineBackend::persist`
  skips the write while the flash fingerprint (`Machine::nv_fingerprint`) equals the one on
  disk, so eframe's 30 s auto-save costs a hash, not a 16 MiB write and sync, on the UI
  thread. `FakeBackend` gained `needing_provision`, `failing_provision`, `provision_gate`,
  `named` and `FakeProbe::provisions`.
- **A4. The LCD tint follows a curve, not the raw PWM duty.** `backlight_tint` maps a lit
  backlight to `0.75 + 0.25·√duty` (black when off), so OS 7.1's default duty (about 0.46)
  reads as white (about 92 %) instead of mid-gray. Screenshots stay undimmed.
- **A5. Tests added beyond the File Structure list:** `tests/real_os.rs` (the real OS in the
  GUI: first-run provisioning, home screen, keypad typing; each test skips without
  `EVO_OS_IMAGE`), and `tests/common/mod.rs` (`TempDir`, shared by the tests that write files).

## Review Focus

1. **A mouse tap shorter than the OS's keypad scan.** A click can deliver press and release in the same UI frame, so the guest would see a 0-cycle press. Expected: every press is held for at least `MIN_HOLD_CYCLES` of emulated time. Tests: Task 3 `tap_is_held_for_min_hold`; Task 6 `clicking_a_key_taps_it` (press and release in separate frames) and `same_frame_tap_is_held` (both in one frame).
2. **The window loses focus while a PC key is held,** or the shift state changes before release. Expected: no stuck calculator key; focus loss releases everything. Tests in Task 4 (`focus_loss_releases_all`, `release_after_shift_lifted_releases_the_pressed_key`).
3. **Typing into a debug text field or capturing a rebinding.** Expected: the keystrokes do not press calculator keys. Tests: Task 4 `typing_suppresses_presses_not_releases`; Task 8 `typing_in_memory_address_does_not_press_keys`; Task 9 `rebinding_via_window`.
4. **The emulator is slower than real time, a frame stalls, or the CPU sleeps.** Expected: no catch-up death spiral, no busy loop while the guest is idle; the UI stays responsive. Tests in Task 3 (`budget_caps_long_frames`, `run_frame_stops_at_wall_budget`, `slow_chunk_shrinks_the_next`, `run_frame_returns_on_idle`).
5. **A missing, truncated, foreign or corrupt save-state slot, or a slot loaded while a key is held.** Expected: an error toast and an unchanged machine; after a good load no key is stuck. Tests in Task 7 (`garbage_file_is_rejected_unchanged`, `corrupt_payload_rejected_unchanged`, `state_from_other_backend_rejected`, `loading_corrupt_slot_shows_error_toast`, `load_while_key_held_releases_keys`).

**Latch rules.** A press of a key that is not down emits `(key,true)` and records `pressed_at`; a press from a second source only adds the source. A release removes its source. Once no source remains, the key is released at `max(now, pressed_at + MIN_HOLD_CYCLES)`. A press during a pending release cancels it and emits nothing. `clear` exists for resynchronising after a reset or a state load, where `cycles()` jumps; the app then releases every key in the backend itself (Task 7).

**`FrameRunner::run`.** Runs `run_for(min(chunk, remaining))` repeatedly. `elapsed()` (wall time since the frame started) is called exactly once after each chunk and never before the first chunk. It counts cycles from the difference in `b.cycles()`. It returns when:
- the budget is used up;
- the status `is_stop()` or is `Idle`;
- a chunk advanced `cycles()` by 0;
- `elapsed() >= wall`.

After each chunk, before deciding whether to return, it adapts: if that chunk took more than `WALL_BUDGET / 4` (chunk time = this `elapsed()` minus the previous one, or minus 0 for the first), `chunk = max(chunk / 2, MIN_CHUNK_CYCLES)`; if it took less than `WALL_BUDGET / 16`, `chunk = min(chunk * 2, CHUNK_CYCLES)`.
